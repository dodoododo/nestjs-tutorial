# Comment database foundation

PR5 Commit 1 adds only the Comment entity, manual migration and database tests.
Comments HTTP endpoints, DTOs, services and shared profile helpers belong to later
checkpoints. Existing Article queries and historical migrations are unchanged.

## Schema and identity

`comments` stores:

- `id`: UUID primary key, mapped to MySQL `varchar(36)` and generated by TypeORM.
- `article_id`: required UUID referencing `articles.id`.
- `author_id`: required UUID referencing `users.id`.
- `body`: required MySQL `TEXT`.
- `created_at`: required `datetime(3)`, default `CURRENT_TIMESTAMP(3)`.
- `updated_at`: required `datetime(3)`, default and automatic update
  `CURRENT_TIMESTAMP(3)`.

The entity uses explicit non-eager `ManyToOne` relations to Article and User,
without ORM cascade persistence or inverse collections. `comments.article_id`
is the authoritative article relationship; Article has no comment ID array or
duplicate relationship storage. Future services query comments by `articleId`.

Comment IDs follow the project's UUID convention. Although the
[RealWorld comment response examples](https://realworld-docs.netlify.app/specifications/backend/api-response-format/#single-comment)
use numeric IDs, this implementation will expose the Comment UUID as a string.
Future DELETE requests must validate UUID syntax before querying. Public comment
responses should contain only `id`, `createdAt`, `updatedAt`, `body` and the author
profile (`username`, `bio`, `image`, `following`); do not serialize entity relations
or expose the internal Article/User UUIDs or password hashes.

## Foreign keys and indexes

`FK_comments_article_id` and `FK_comments_author_id` use `ON DELETE CASCADE`
and `ON UPDATE RESTRICT`. Deleting an Article removes its comments; deleting a
User removes comments they authored, including comments on other users' articles.
Both cascade paths also work when the deleted user owns a commented article.
Deleting a Comment leaves its parents and other records intact. No application
cleanup is needed for these relationships.

`IDX_comments_article_created_at_id (article_id, created_at, id)` supports the
future query `WHERE article_id = ? ORDER BY created_at DESC, id DESC`. With the
article fixed, MySQL can scan the ascending index backward for both descending
sort keys. The UUID tie breaker makes ordering deterministic at millisecond ties.
This index also supplies the article foreign key's leading column; a separate
article-only index would be redundant.

`IDX_comments_author_id (author_id)` supports the author foreign key and cascading
author deletion. Both secondary indexes are nonunique: a user can write multiple
comments on the same article.

## Body validation for the next checkpoints

MySQL `TEXT` holds at most **65,535 bytes**, not 65,535 Unicode characters. No
smaller application limit is introduced. The database enforces non-null content
but allows empty or whitespace-only strings. Strict SQL mode rejects oversized
values; the isolated database tests verify that mode before testing capacity.

The future Create Comment DTO must require a string, reject empty and
whitespace-only input, preserve meaningful whitespace/formatting, and check
`Buffer.byteLength(body, 'utf8') <= 65_535` before persistence. Return HTTP 400 for
invalid or oversized input. Character-count decorators such as `@MaxLength`
cannot replace this byte check. Tests cover ASCII, multibyte Unicode and emoji
at and beyond the database boundary. No DTO or HTTP validation is implemented
in this checkpoint.

## Manual migration and verification

`1795251668000-CreateComments.ts` follows the Articles migration. `up` creates
only `comments`, its primary key, two secondary indexes and two foreign keys.
`down` drops `comments`, including any comments it contains. Other tables and
historical migrations are untouched. Both `synchronize` and `migrationsRun`
remain `false`; normal application startup does not apply this migration.

MySQL DDL can implicitly commit and cannot be protected by a complete
transactional rollback. Migration checks use `transaction: 'none'`, verify actual
schema and migration history, and restore pending migrations in `finally`.
Reapplying a reverted migration recreates an empty table; it does not recover
deleted comments. Re-running migrations with no pending migration is a no-op.

The database E2E suite first verifies `NODE_ENV=test`, MySQL at
`127.0.0.1:3308/nestjs_tutorial_test`, Redis at `127.0.0.1:6380`, and disabled schema
synchronization/automatic migrations, before fixture writes or DDL. Historical
migrations must already be applied. The focused Comment suite can apply only the
new Comments migration and refuses any other pending migration.

Run on Node.js 26.13.0:

```powershell
npm.cmd run test:e2e -- --runInBand comment-database.e2e-spec.ts
npm.cmd run test:e2e -- --runInBand article-database.e2e-spec.ts
npm.cmd run format
npm.cmd run lint
npm.cmd run build
npm.cmd test -- --runInBand
npm.cmd run test:e2e -- --runInBand
git diff --check
```

Migration roundtrips refuse to drop nonempty target tables. The Comment suite
compares hashed snapshots of existing PR2/PR3/PR4 rows and schemas before and
after rollback/reapply, including fixtures for users, follows, attachments,
articles, tags and favorites. Cleanup targets only test-created records. The
existing Article migration test now reverts the dependent, empty Comments table
before reverting Articles, then restores both migrations. Run these suites
serially because their migration checks change the isolated schema. Never run
destructive verification against development or production databases.

## Later service requirements

Future Delete Comment should find the Article and Comment, verify article
membership and authorship, then issue a simple scoped DELETE. Unknown or
cross-article IDs return 404; another author returns 403. No speculative locks or
transactions are added here. Future service tests must also cover creation for an
unknown slug (404), malformed input and authentication cases.

Future response construction should reuse suitable profile mapping, keep mappers
pure and batch following lookups to avoid N+1 queries. This checkpoint neither
adds those helpers nor modifies the optimized ArticlesService queries.
